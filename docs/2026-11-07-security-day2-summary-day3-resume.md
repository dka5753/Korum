# Spring Security 2일차 정리와 3일차 이어하기

학습일: 2026-11-06~2026-11-07 (한국 시간)

## 지금 어디까지 했나

2일차의 React 폼 로그인·세션·로그아웃 실습을 마쳤다. 3일차는 인증과 인가, 작성자 검사의 필요성을 대화로 확인했고 구현은 시작하지 않았다.

학습자는 코드를 읽으면 이해하지만 직접 작성할 때 힌트가 필요하다. 작은 빈칸이나 단계별 힌트를 제공하고, 직접 작성한 코드를 리뷰하며 이유를 말로 설명하는 방식으로 이어간다. 완성 기능을 한꺼번에 구현하지 않는다.

## 자료와 Korum 적용 범위

- 자료: 제공된 `09_spring_security/practice/09_02/09_02_실습_튜토리얼.md`의 4~6단계와 `09_03/09_03_실습_튜토리얼.md`.
- 자료 내용: 폼 로그인, 세션, 로그아웃, 세션 ID 변경, 필터 흐름. 다음은 URL 인가·메서드 보안·소유자 검사다.
- Korum 보충: Java 예제를 Kotlin에 적용하고 MariaDB를 유지했다. CSRF를 켠 채 React 요청을 연결했다. Basic 재인증을 막기 위해 Basic을 끄고 미인증 API 요청에는 401을 반환했다.
- 이번 자료 확인은 일일 구성표와 실습 튜토리얼 중심이다. PDF 전체 내용을 새로 검토했다고 기록하지 않는다.

## 구현한 요청 흐름

1. `GET /csrf`: 쿠키를 포함해 토큰을 받는다.
2. `POST /api/login`: `URLSearchParams`로 username/password를 보내고 CSRF 헤더를 포함한다. 성공200·실패401로 설정했다.
3. `GET /me`: Basic 헤더 없이 `credentials: "include"`로 세션 쿠키를 보낸다.
4. `POST /api/logout`: 새로 받은 CSRF 토큰과 쿠키를 보낸다. 기본 로그아웃 처리가 세션을 무효화하고 성공 핸들러가 200을 반환한다.
5. 로그아웃 후 `GET /me`: `authenticationEntryPoint`가 401을 반환한다.

변경 파일은 `SecurityConfig.kt`, `App.tsx`다. 로그인·회원가입 값은 아직 고정 실습값이며 사용자 입력 UI는 없다.

## 직접 확인한 결과

| 확인 | 결과와 근거 |
|---|---|
| 로그인 | 브라우저 Console 200, 사용자 제공 로그 |
| 세션 내 정보 | `{username: 'user'}`, 사용자 제공 로그 |
| 로그아웃 | 200, 사용자 제공 로그 |
| 로그아웃 후 조회 | 401, 사용자 제공 로그 |
| 로그인 전후 세션 ID | 값이 바뀜, 사용자 확인. 원문은 저장하지 않음 |
| 보안 필터 진입 | `Securing POST /api/login`, `Securing GET /me`를 사용자 확인 |

비밀번호가 틀린 폼 로그인은 실패401로 설정했으나 이번 실습에서 별도로 재확인했다고 기록하지 않는다. 필터 진입 로그 확인과 내부 모든 필터·인증 제공자 호출 추적 완료는 구분한다. 로그아웃200 뒤 조회401이 실제 성공 기준이며 자동 통합 테스트 결과는 아니다.

저장 전 `npm run build`, `gradlew.bat compileKotlin`, `git diff --check`가 통과했다. 자동 통합 테스트는 실행하지 않았다. 기존 작업의 Actuator 의존성 추가와 npm 잠금 파일의 peer 메타데이터 변경도 함께 보존했다. Actuator 별도 동작 검증은 하지 않았다.

## 핵심 개념 복습

- Basic은 요청마다 아이디·비밀번호를 담은 헤더로 인증한다. Base64는 암호화가 아니다.
- 세션 인증은 서버에 인증 정보를 저장하고 브라우저가 세션 ID 쿠키를 보내 이를 찾는다.
- 로그아웃은 서버 연결을 끊는 일이 아니다. 인증된 세션을 무효화하는 일이다. 서버에 도착하지 못한 연결 오류와 서버가 응답한 401은 다르다.
- `/posts`는 `permitAll()`이므로 인증 정보 없이도 접근할 수 있다.
- 로그인할 때 세션 ID를 바꾸는 것은 세션 고정 공격 방어다. DB 사용자 ID는 그대로다.
- BCrypt는 복호화 키가 없는 단방향 해시다. `encode()`마다 무작위 솔트가 달라진다. 날짜·시간으로 솔트를 직접 만들지 않는다.
- 로그인 검증은 `encode(input) == storedHash`가 아니라 `matches(input, storedHash)`로 한다. 저장된 해시에는 솔트와 비용 설정이 포함된다.
- `JpaUserDetailsService`는 DB 사용자를 조회해 `UserDetails`로 변환한다. 인증 제공자가 비밀번호 검증을 연결한다.
- 로그인 필터 → 인증 제공자 → 사용자 조회·비밀번호 검증 → 세션 인증 정보 저장 → 성공 응답으로 이어진다. 이후 세션 조회마다 비밀번호를 다시 검증하지 않는다.
- `failureHandler`는 로그인 시도 실패를, `authenticationEntryPoint`는 미인증 보호 자원 접근을 처리한다.

## 해결한 문제

| 현상 | 확인·조치 |
|---|---|
| JSX의 함수 이름 오류 | `handlelogin`을 `handleLogin`으로 수정 |
| TS6133 미사용 headers | 기존 Basic용 변수 제거 |
| DB Dialect 오류·Access denied | DB 접속 인증 실패를 먼저 확인. `.env`와 컨테이너 설정 일치 및 DB 사용자 조회 성공 확인 후 IntelliJ 환경 변수 안내 |
| `ERR_CONNECTION_REFUSED` | 백엔드 8080 실행 여부 확인. npm은 프런트만 실행함 |
| 로그아웃200 뒤에도 user 조회 | 실제 요청에 Basic 헤더가 있음을 사용자 확인. 백엔드 Basic 비활성화 후 재확인 |
| `Unexpected token '<'` | 미인증 조회가 로그인 HTML을 받은 현상. API 진입점을 401 응답으로 설정 |
| Console의 빨간 401 | 정상 접근 거절이나 현재 React에서 예외를 잡지 않아 빨간 오류로 출력됨. 오류 UI는 후속 과제 |

## 다음 시작점 — 3일차 작성자와 소유자 검사

현재 `CreatePostRequest.author`를 클라이언트가 보내고 서버가 저장한다. 로그인한 사용자를 작성자로 자동 저장하지 않으며, 본인 글 검사도 아직 없다.

이해한 내용:

- `authenticated()`는 인증 여부를 확인하며 본인 글인지는 확인하지 않는다.
- `hasRole("ADMIN")`은 관리자 역할 검사다.
- 작성자 정보는 DB와 조회 응답에는 필요하지만, 글쓰기 요청의 작성자는 사용자가 바꿀 수 있다.
- 요청 author를 로그인 이름과 비교하는 검사는 가능하지만, 서버가 이미 로그인 이름을 알므로 작성 시 서버의 인증 정보를 직접 사용하면 된다.

마지막에 학습자가 물은 “1차로 걸러준다”는 요청의 author를 먼저 검사하는 방식을 뜻했다. 위 설명까지 했으며 아래 질문의 답은 아직 받지 않았다.

> DB에 작성자가 user인 글을 kim이 삭제하려 한다. 서버는 어떤 두 값을 비교해야 할까?

이 질문부터 짧게 복습한 다음 순서대로 진행한다.

1. `PostController.createPost`와 `BoardService.createPost`, `CreatePostRequest`를 함께 읽는다.
2. `/me`에서 사용한 `Principal`을 힌트로 작성자를 서버에서 정하도록 직접 작성한다.
3. 글쓰기 요청 DTO의 author 제거와 저장 모델·응답의 author 유지를 구분한다.
4. React 글쓰기와 CSRF 요청을 연결하고 실제 저장 작성자를 확인한다.
5. 자료 3일차 순서에 맞춰 URL 규칙·메서드 보안·본인 글 검사로 이어간다. 관리자 예외 정책도 자료와 비교한다.

## 다시 실행하기

1. Docker Desktop 실행 후 프로젝트 루트에서 `docker compose up -d mariadb`.
2. IntelliJ에서 `KorumApplication.kt`의 main 실행. 환경 변수 `DB_PASSWORD`는 로컬 `.env` 값과 동일하게 설정한다. 비밀번호를 문서나 Git에 복사하지 않는다.
3. 별도 터미널에서 `cd korum-frontend`, `npm run dev`.
4. 프런트 주소는 CORS 설정과 같은 `http://localhost:5173`을 사용한다.
5. 세 프로세스를 함께 유지한다. 기존 DB 볼륨은 삭제하지 않는다.

## 다음 대화 시작 문장

> Korum Spring Security 이어서 하자. 2일차 세션 로그인·조회·로그아웃401, 세션 ID 변경, 필터 진입 로그까지 확인했어. 3일차에서 요청 author를 믿으면 안 되는 이유까지 배웠고 아직 코드는 안 바꿨어. 작성자와 로그인 사용자 비교 질문부터 복습하고, 힌트를 주면 내가 직접 작성하는 방식으로 진행해줘.
