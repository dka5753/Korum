## A. 회원가입 기능 작성

### A-1. 입력값 검증

`SignupService.signup(request)`에서 먼저 잘못된 입력을 거절한다.

실습 기준:

- email이 공백이면 거절
- username이 공백이면 거절
- password가 4자 미만이면 거절

4자 기준은 교안 흐름을 확인하기 위한 실습 조건이지 실제 서비스용 비밀번호 정책이 아니다.

힌트:

- `request.username`처럼 DTO의 값을 읽는다.
- `isBlank()`로 공백 여부를 검사한다.
- 문자열의 `length`로 길이를 확인한다.
- 조건을 `||`로 연결할 수 있다.

입력 오류를 예외로 표현한다면 전용 예외를 만들고 컨트롤러 조언에서 **400**으로 연결한다. 예외만 던지고 매핑하지 않으면 500이 될 수 있다.

- [ ] 검증 조건 작성 후 코드 리뷰

### A-2. 사용자 이름 중복 검사

이미 작성한 저장소 함수를 재사용한다.

```kotlin
users.findByUsername(request.username)
```

반환값이 null이 아니면 이미 있는 계정이다. 초기화 코드의 `== null` 조건과 비교해보면 된다.

중복 전용 예외를 사용하고 **409 Conflict**에 연결한다. 이번에는 사용자 이름 중복만 다룬다. 이메일 중복 정책과 DB 고유 제약·동시 요청 처리는 별도 보완 범위다.

- [ ] 기존 `GlobalExceptionHandler`에 입력 오류 400·중복 409 매핑 추가

### A-3. 비밀번호 해시와 DB 저장

`DataInitializer`에서 했던 것과 같은 흐름이다. 이번에는 고정값 대신 요청값을 사용한다.

| User 필드 | 넣을 값 |
|---|---|
| email | `request.email` |
| username | `request.username` |
| password | `checkNotNull(encoder.encode(request.password))` |
| role | 서버에서 고정한 `"USER"` |

## B. CORS·쿠키·CSRF 요청 준비

### 교안과 Korum의 차이

원본 2일차 교안은 CSRF 차단을 관찰한 후 보호를 잠시 끄고, 4일차에 다시 켜서 공격·방어를 실습한다.

이 가이드는 이미 CSRF에 관해 질문한 흐름에 맞춰 **보호를 유지하고 토큰을 포함하는 경로**를 선택했다. 다음 구성은 Korum용 추가 연결 단계이며, 아직 완성된 코드가 아니다. 전체 CSRF 공격 실습은 여전히 4일차 범위다.

### B-1. 쿠키를 포함하는 CORS 설정

어제 Basic 요청은 `credentials: "omit"`이었다. 오늘 폼 세션 방식은 `credentials: "include"`로 쿠키를 주고받는다.

서버 측 CORS에도 다음이 필요하다.

- 허용 Origin: 정확히 `http://localhost:5173`
- 허용 메서드: 사용할 GET·POST 등
- 허용 헤더: Content-Type과 CSRF 헤더 등
- `allowCredentials(true)`
- 기존 `http.cors(Customizer.withDefaults())` 유지

쿠키를 허용할 때 허용 Origin을 `*`로 설정하지 않는다. 설정은 `WebMvcConfigurer`를 구현한 WebConfig에서 필요한 경로를 한 번에 구성하는 방식으로 정리한다. 기존 컨트롤러의 `@CrossOrigin`과 중복되는 항목은 최종 유효 설정을 함께 확인한다.

- [ ] WebConfig의 CORS 설정을 리뷰받기
- [ ] React의 실제 Local 주소가 5173인지 확인

### B-2. CSRF 토큰 조회 API

GET `/csrf`를 추가한다. 이 주소는 미로그인 상태에서도 접근하도록 GET 공개 규칙을 넣는다.

힌트:

- 함수 매개변수 타입: `org.springframework.security.web.csrf.CsrfToken`
- 스프링이 제공하는 토큰 객체에서 `token`, `headerName`을 응답으로 전달
- 세션 쿠키를 받을 수 있게 프런트 fetch에 `credentials: "include"` 사용
- 토큰이나 쿠키 값을 console.log로 기록하거나 채팅에 복사하지 않기

React는 응답의 `headerName`과 `token`을 사용해 다음 POST 요청의 헤더를 구성한다. GET 토큰 조회와 POST는 같은 세션 쿠키를 사용해야 한다.

```text
GET /csrf + credentials include
 → 응답에서 token·headerName 받기
 → POST /signup에 해당 헤더와 같은 세션 쿠키 포함
```

로그인·로그아웃 후에는 이전 토큰이 지워질 수 있으므로 새 토큰을 받는다. 첫 구현은 변경 요청 전에 토큰을 조회하는 공통 함수를 만드는 방식으로 진행한다.

- [ ] `/csrf` 컨트롤러 작성·리뷰
- [ ] 토큰 GET 공개 규칙 추가
- [ ] 프런트 토큰 조회 함수 작성·리뷰

## D. React에서 폼 로그인과 세션 사용

브라우저 기본 로그인 화면은 이미 실습했다. 남은 목표는 **React가 로그인 요청을 보내고, 이후 비밀번호 없이 쿠키로 `/me`를 조회하는 것**이다.

### D-1. 백엔드 로그인 응답 구성

`formLogin` 설정에서 다음 항목을 직접 구성한다.

| 설정 | 목표 |
|---|---|
| loginProcessingUrl | `/api/login` |

- [ ] 로그인한 username이 응답에 나오는지 확인

## E. 로그아웃과 세션

1. 로그인된 같은 브라우저 세션에서 새 CSRF 토큰을 받는다.
2. POST `/api/logout`에 credentials include와 토큰 헤더를 포함한다.
3. 200 확인 후 `/me`를 다시 요청한다.
4. 미로그인 요청으로 거절되는지 확인한다. API JSON 요청에서는 401을 예상하되 리다이렉트가 보이면 요청 헤더·보안 진입점 설정도 확인한다.

쿠키가 화면에 남아 있어도 서버 세션은 무효화됐을 수 있다. 새 일반 탭은 기존 쿠키를 공유할 수 있으므로 새 탭만으로 로그아웃 여부를 판단하지 않는다.

### 로그인 전후 세션 ID 비교

- 로그인 전에 credentials include로 `/csrf`를 호출해 세션을 준비한다.
- 개발자 도구에서 세션 ID를 눈으로 확인한다.
- 폼 로그인 성공 후 다시 확인한다.
- 기본 세션 고정 보호로 ID가 변경되는지 관찰한다.

세션 ID 원문은 노트·Git·채팅에 저장하지 않는다. 기록에는 `로그인 전후 값이 달라짐`처럼 결과만 적는다.

- [ ] 로그아웃 후 보호된 요청 거절
- [ ] 로그인 전후 세션 ID 변화 관찰

## F. 필터 로그 복습

현재 보안 TRACE 설정을 이용해 다음 요청들을 각각 찾는다.

```text
Securing POST /api/login
Securing GET /me
```

찾을 핵심 역할:

| 구성 요소 | 역할 |
|---|---|
| CsrfFilter | 변경 요청 토큰 검증 |
| UsernamePasswordAuthenticationFilter | 폼 로그인 요청의 아이디·비밀번호 추출 |
| DaoAuthenticationProvider | 사용자 조회와 비밀번호 검증 연결 |
| JpaUserDetailsService | DB 사용자 조회·UserDetails 변환 |
| PasswordEncoder.matches | 입력 비밀번호와 저장 해시 검증 |
| SecurityContext 관련 필터·저장소 | 인증 정보의 세션 저장·조회 |
| AuthorizationFilter | 요청별 접근 조건 검사 |

`DaoAuthenticationProvider`는 필터 자체가 아니다. 로그인 필터가 인증 처리를 위임하는 구성 요소다.

Korum은 교안과 버전·설정이 다르고 CSRF를 유지하므로 필터 개수와 순서를 교안 숫자에 맞추지 않는다. `/error` 후속 요청과 원래 API 요청도 구분한다.

복습 질문:

1. 비밀번호 해시는 언제 생성하고 로그인 때는 어떤 메서드로 검증하는가?
2. `JpaUserDetailsService`가 반환하는 것은 DB 엔티티인가, 로그인용 UserDetails인가?
3. 세션 `/me` 요청에 비밀번호가 없는데 서버가 사용자를 아는 이유는?
4. CSRF 토큰과 세션 ID의 역할은 어떻게 다른가?
5. 일반 사용자 403과 존재하지 않는 주소 404는 무엇이 다른가?
